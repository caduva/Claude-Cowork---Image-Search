03 — Escopo dos desenvolvedores

Decisão: nada além do que a Muralis já está construindo

A Muralis (FSE-01_2026) é o único desenvolvimento contratado, e cobre o KPI 4. Para os quatro KPIs que precisam de dado novo (7, 8, 11, 14), a decisão é não pedir nada a nenhum time de dev. Todos se resolvem com captura própria no frontend, seguindo o mesmo padrão: um evento pequeno, disparado no momento certo, gravado num endpoint e banco que você controla.

KPI 4 está coberto pela Muralis. A avaliação deles é Ótima/Ok/Ruim com estado de remoção, chave por obra-tópico — diferente do desenho conceitual anterior (1/2/3 sem remoção, chave por imagem+tópico). Vale confirmar o mapeamento exato de campo quando a tabela deles aparecer no dicionário de dados — hoje ainda não aparece (última atualização documentada é de 01/07/2026, a proposta foi assinada em 07/07/2026).

Os quatro que precisam de captura própria: nenhum precisa do time de dev

  • KPI 7 — Profundidade de Navegação: evento SCREEN_NAV a cada troca de rota no frontend.
  • KPI 8 — Perfil de Curadoria, renomeação de pasta: favorite_collections só guarda o nome atual, sem log de mudança. Em vez de aproximar por snapshot, o frontend dispara um evento FOLDER_RENAMED no momento exato em que a pessoa renomeia — mesmo padrão do KPI 7, com timestamp exato em vez de aproximado.
  • KPI 11 — Qualidade do Enrich, motivação: o texto (interest) existe só de passagem na chamada que o frontend faz pro backend, e nunca é salvo. O frontend manda esse texto também pro endpoint próprio, em paralelo à chamada normal, como evento ENRICH_MOTIVATION.
  • KPI 14 — Tempo Ativo, o core do KPI: confirmei no código que sessions.last_seen_at só atualiza a cada renovação de sessão, não a cada ação da pessoa — não serve para medir tempo ativo. A solução: evento ACTIVITY_HEARTBEAT — o frontend detecta atividade real (teclado, scroll, clique) e manda um ping a cada ~30s enquanto a pessoa está ativa; tempo ativo = número de pings × intervalo. O mesmo evento carrega o tipo de dispositivo, detectado direto no navegador.

Resultado: o único ponto de contato necessário com um time de dev externo continua sendo a Muralis, e só para o KPI 4. Os quatro tipos de evento (SCREEN_NAV, FOLDER_RENAMED, ENRICH_MOTIVATION, ACTIVITY_HEARTBEAT) ficam todos numa única tabela própria, alimentada por pequenas mudanças no fuse-frontend — nenhuma delas passa pelo backend da Fuse.

04 — Opções de arquitetura

Extração SQL do MySQL real como base, captura própria só para o que falta

Com 10 KPIs resolvidos direto do banco de produção, o projeto é principalmente um extrator, mais uma captura própria pequena e específica para os quatro sinais que realmente não existem (7, 8, 11, 14).

recomendada

Stack recomendada — decidido: dentro da mesma conta AWS da Fuse

A Fuse já roda inteira na AWS (RDS MySQL, VPC, ECS para tarefas avulsas). Decisão: colocar a infra do painel na mesma conta, para o extrator acessar o banco de produção por rede privada — sem expor o RDS publicamente nem depender de um provedor externo (descartada a opção Supabase/Neon considerada antes).

  • Banco do painel: RDS Postgres db.t4g.micro, single-AZ, 20GB gp3 — instância nova e separada do RDS de produção da Fuse, mesma conta e VPC (ou peered)
  • Extrator: Lambda + EventBridge Scheduler (ou uma ECS Fargate Scheduled Task, mesmo padrão já usado nas tarefas avulsas da Fuse), leitura direta do MySQL de produção por rede privada
  • Captura de evento próprio: Lambda Function URL como endpoint, gravando numa tabela fuse_events — quatro tipos de evento, sem tocar no backend da Fuse
  • Separação de custo: tag Project=fuse-kpis-dashboard em todo recurso, ativada como Cost Allocation Tag no Billing — mesma conta da Fuse, custo visível à parte
  • Cuidado: evitar NAT Gateway (~US$32/mês) — o extrator só precisa falar com o RDS dentro da VPC; usar VPC endpoints em vez de saída para internet
  • BI aberto: Metabase, auto-hospedado (Docker/Railway) ou Cloud free tier
  • Dashboard final: Next.js vibe-coded na Vercel, consultando o Postgres via API própria

Custo estimado: ~US$15–20/mês (RDS + Lambda/ECS + EventBridge, sem NAT Gateway).

06 — Ferramenta de mercado vs. vibe code

Por que decidimos não contratar uma ferramenta pronta

A ideia de usar uma ferramenta pronta (tipo PostHog, Mixpanel ou Amplitude) surgiu de um problema real — a proposta que a Muralis apresentou pra construir esses indicadores era cara e "artesanal": cada indicador seria feito sob medida no código, e qualquer tela ou funcionalidade nova no app exigiria um novo desenvolvimento só pra ajustar ou criar um indicador. Isso preocupava, porque a manutenção ficaria cara e lenta com o tempo — daí a busca por uma ferramenta de mercado que resolvesse isso de forma mais flexível.

Só que, ao investigar o banco de dados real da Fuse, descobrimos que a maior parte da informação que os indicadores precisam já existe — guardada nas tabelas que o próprio aplicativo usa pra funcionar (conversas do chat, favoritos, notificações etc.), como consequência natural de funcionalidades que já existem, não como um projeto de métricas à parte. Isso muda a conta: contratar uma ferramenta agora significaria pagar por assinatura e reconstruir do zero uma captura de dados que, na maior parte dos casos, já está disponível.

Dos 15 indicadores, só 4 realmente precisam de algo novo sendo registrado — e são pequenos o suficiente para resolver com uma solução simples e própria, sem custo de assinatura nem depender de mais um fornecedor. Decisão: construir tudo internamente. Extrair o que já existe, e criar uma captura simples e própria só para os 4 pontos que faltam.

Recomendação: não contratar nenhuma ferramenta de mercado agora. Construir o extrator SQL primeiro — ele sozinho entrega 10 dos 15 KPIs. Resolver os quatro sinais que faltam com a tabela de eventos própria, criada e mantida por você via vibe code. Guardar PostHog na manga como opção só se, mais adiante, o volume de KPIs futuros justificar uma plataforma inteira — não antes disso.

07 — Ponto de atenção

Dado sensível no banco real

chat_messages.message, philosophical_analyses.prompt_text/reflection_text, favorite_uploads.text_content, e favorites.prompt_context guardam texto literal do que a pessoa escreveu — incluindo reflexões pessoais. Isso é dado pessoal sensível sob a LGPD, espalhado por várias tabelas.

Recomendo: criptografia em repouso no fuse-kpis-db; controle de acesso por papel (agregados no Metabase para o time de produto, texto verbatim só para quem precisar de revisão qualitativa); política de retenção definida antes do extrator rodar pela primeira vez. Como a extração é toda via SQL direto — sem rotear esse texto por nenhum SaaS terceiro — o risco de exposição já fica mais contido do que seria com uma plataforma de eventos na frente.
